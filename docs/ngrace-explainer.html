Graph-RAG Anchored Code Engineering · v5.0.0

Your agent is
confidently wrong.

It claims a function is exported when it isn't. It reports a module as tested when nothing runs it. GRACE is a machine-checked model of your project that catches the claim at the moment it's made.

Every fact carries its evidence
01

The whole idea, in one diff

A developer — or an agent — documents a Go module. One of the two exports listed below does not exist. Nothing about the claim looks wrong.

Asserted, unchecked 
// START_MODULE_MAP
//   Route    - Dispatch a request.
//   Shutdown - Stop the router.
// END_MODULE_MAP

Plausible, well-formed, and reviewed by a human who had no reason to doubt it. In a plain repository this survives indefinitely, and every later agent treats it as ground truth.

Checked against the source 
$ ngrace lint

[error] markup.module-map-mismatch
  services/api/…/router.go:10
  Missing: none; extra: Shutdown.

GRACE lexed the Go file, collected its exported identifiers, and disagreed. Not a naming convention and not a heuristic — a parse. The same holds for Rust and TypeScript.

The rule everything else follows from.

Documentation that contradicts the code is a build error. Once that is true, the model of your project stops being a wiki that decays and starts being something an agent can safely act on.

02

Four stores, one directory

Everything GRACE knows lives in .ngrace/, versioned beside your code and validated on every run. Four stores, each answering a different question.

context/

What is true about this project regardless of any single change — requirements, principles, technology, design system, invariants.

slow-moving
graph/

What exists and how it connects: modules, data flows, and the interface contracts between services.

the map
verification/

What proves each module works — commands, scenarios, log markers, accessibility and visual checks.

the evidence
changes/

What is being changed right now and what was changed before, each as an approved spec and a gated plan.

the ledger

The graph is segmented: a large project splits it across ui.xml, api.xml, core.xml and so on, with an index declaring which document owns which anchor. GRACE assembles them into one logical view, so file layout never constrains the model.

03

Anchors are the vocabulary

Every addressable thing has a canonical name that is an XML tag, never an attribute — so a reference to it is unambiguous everywhere it appears.

FamilyNamesExample
M-*A module — a unit of behaviour with an owner and a pathM-WEB-LEDGER-TABLE
V-M-*The evidence that proves a module worksV-M-WEB-LEDGER-TABLE
DF-*A data flow — an ordered path across modulesDF-POSTING
IC-*An interface contract between services, with a schema and a versionIC-POSTING-V1
AC-*An acceptance criterion a task can point atAC-KEYBOARD-NAV
ST-*A UI state that must have evidenceST-ERROR
INV-*An invariant that outlives any single changeINV-IDEMPOTENT-POST

You will not type these.

The skills author the XML; you approve it. This table is here so the diagnostics make sense when you read them, not because the vocabulary is homework.

04

A change is a chain, and each link is gated

Order matters here, so the steps are numbered. Nothing advances because an agent believes it should — it advances because a check passed.

01
Spec — what and why

An interview produces spec.xml as a draft: goals, constraints, non-goals, affected modules, and addressable acceptance criteria.

Gate · you approve
02
Plan — how, and what proves it

plan.xml declares the write scope, the tasks, and machine-checkable assertions. Its scope must cover the spec that authorised it, or lint fails.

Gate · you approve
03
Execute — implement under the plan

Tasks run in dependency order. The plan is immutable once approved; the agent works inside a blast radius you already agreed to.

Gate · assertions must pass
04
Verify and archive

Evidence is collected against the verification model, and the bundle moves to the archive — a permanent record of what was approved beside what was actually done.

Gate · final assertions

Not every change deserves the same paperwork. Four ceremony tiers — hotfix through architectural — change how much you write, never whether the gates run. There is deliberately no way to skip GRACE: the moment one exists, everything becomes an emergency.

05

What the tool refuses to guess

The failure worth designing against is not a missing check. It is a check that reports success without having looked.

ngrace doctorhonesty surface
Analysis coverage
  Governed files: 3
  Adapter-backed: .go×1, .rs×1, .tsx×1
  Unverified: (none)

Optional context artifacts
  - design-system.xml: present
  - invariants.xml: present

When a file's language has no export adapter, it is listed under Unverified rather than silently passing. A module whose evidence cannot be confirmed is reported as unconfirmed, not as healthy. Knowing the boundary of what a tool has actually verified is the difference between a model you can delegate against and one you merely hope is right.

06

Three decisions stay yours

GRACE automates the bookkeeping, not the judgement. Everything else the skills handle; these three are the ones a tool should never take.

i
Approving the spec

Scope is decided here. Nothing reaches approved without you saying so.

ii
Approving the plan

The definition of done is decided here — as commands and checks, not adjectives.

iii
Deciding what a failed gate means

GRACE reports and refuses. It does not overrule you, and it does not quietly proceed.
